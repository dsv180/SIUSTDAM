# Задание: интеграция TDAM с Active Directory

> **Составил:** AI по замыслу заказчика. **Дата:** 05.11.2026.
> **Статус:** задание сформулировано, реализация НЕ начиналась.
> **Решение о сроках и начале работ** — за заказчиком.
>
> **Что это.** Формулировка цели и задач для доработки TDAM: вход
> сотрудников по доменным учёткам Active Directory. Далее — отдельным
> шагом — граничные условия в рамках общей работы над агентской
> инфраструктурой отдела.

---

## 1. Цель

Дать сотрудникам отдела вход в панель памяти и сервисы TDAM **по доменным
учёткам Active Directory**.

**Ключевое условие ценности:** AD — единственный источник личности; TDAM
не заводит собственных учёток и не хранит пароли. Учётная запись TDAM
появляется **при первом входе**, автоматически; ручная раздача ключей
исключается. Права внутри TDAM распределяются существующей моделью команд.

## 2. Граница задачи

**Что входит:** аутентификация сотрудника по AD → создание/нахождение его
учётной записи в TDAM → выдача рабочей сессии в панель и клиенты памяти.

**Что НЕ входит:** управление пользователями в AD (создание, пароли,
группы — остаётся за службой каталога); замена внутренней модели прав TDAM;
единый вход (SSO) для сторонних систем отдела.

## 3. Проблема, которую решаем

TDAM сейчас знает только собственные учётные записи: личность
подтверждается ключом `user_key` (`sk-mem-...`), который нужно завести и
выдать вручную. В корпоративном контуре это создаёт вторую, параллельную
систему учёта сотрудников: не связана с AD, не отзывается при увольнении,
требует ручной раздачи ключей.

**Следствие:** увольнение или блокировка в AD **не закрывает** доступ к
памяти отдела; учёт сотрудника приходится вести отдельно.

## 4. Что уже есть в TDAM (проверено по исходникам, 04.11.2026)

Авторами уже заложен слой внешних провайдеров идентичности, спроектированный
ровно под такую задачу. Работа — **не строить с нуля**.

### 4.1. Готово и пригодно

| Механизм | Что это | Где |
|---|---|---|
| **Реестр провайдеров** | точка расширения: провайдер регистрируется одной строкой | `MemoryPanel/src/panel/auth/provider-registry.ts` |
| **Контракт header-injected** | провайдер доверяет заголовку от вышестоящего прокси — ровно наш случай | `panel/auth/types.ts` (`HeaderInjectedProvider`) |
| **Рабочий эталон** | WOA-провайдер: header-injected с криптоподписью (JWE) | `panel/auth/woa-provider.ts` |
| **Универсальная ingress-мидлварь** | перебирает header-injected-провайдеров, матчит по имени заголовка — второй провайдер **без правки мидлвари** | `panel/http/routes/auth.ts` |
| **Привязка внешней личности** | поля `auth_provider` + `external_id` в `meta_users`, методы `findUserByExternalId` / `bindExternalIdToUser`, роуты `user/find-by-external`, `user/bind-external`. В коде помечено как заложенное «под SSO» | `MemoryCore/src/metadata/service/metadata-service.ts` |
| **Provisioning** | автосоздание учётки + привязка + default team (`provisionIdentity`) | `panel/auth/service.ts` |
| **Хранилище привязок** | шифрованный store `identity → user` | `panel/auth/identity-store.ts` |
| **Сессии панели** | сессионный слой с cookie; гард принимает либо `user_key`, либо валидную IdP-сессию | `panel/auth/session-store.ts`, `panel/http/middleware/validate-panel-headers.ts` |
| **Домен провайдера** | конфигурационная точка `auth_provider` (например `"ad"`) | `panel/config/panel-config.ts` |

### 4.2. Заложено, но не реализовано

| Механизм | Состояние |
|---|---|
| **Интерфейс OIDC/OAuth2-провайдера** | объявлен, реализации нет (`RedirectOAuth2Provider`) |

### 4.3. Чего нет (наш объём работ)

| Пробел | Суть |
|---|---|
| **AD-провайдер** | ни LDAP, ни Kerberos, ни SAML — ни одной реализации |
| **Проверка доверия к заголовку** | «голый» заголовок не защищён: WOA полагается на криптоподпись, у нас её не будет (см. З3) |
| **Логин по паролю** | в ядре отсутствует (хэш пароля помечен legacy) — осложняет вариант LDAP-синхронизации |
| **Жизненный цикл учётки** | нет реакции TDAM на блокировку/увольнение в AD |

### 4.4. Важное следствие находок

**Ядро (MemoryCore) при интеграции не трогается вообще.** Пользовательская
модель (`auth_provider` + `external_id`) и точка расширения существуют.
Правки — **исключительно в MemoryPanel**, преимущественно аддитивные,
по образцу WOA.

## 6. Задачи (что требуется решить)

**З1. Выбрать схему интеграции (К2).** Развилка:

- **А. Прокси-аутентификация** — Kerberos/Negotiate на реверс-прокси перед
  панелью; панель доверяет заголовку (header-injected). Объём: ядро 0,
  панель ~150–250 строк, обязателен прокси с Kerberos-модулем.
- **Б. LDAP-синхронизация** — тянуть учётки AD в TDAM. В коде почти ноль,
  но требуется свой синхронизатор и свой логин-пароль (в ядре его нет).
- **В. OIDC** — через корпоративный IdP (ADFS/Keycloak), если появится в
  контуре. Объём ~300–500 строк, нужен внешний OIDC-IdP.

**З2. Реализовать AD-провайдер (К3).** По образцу WOA-провайдера, без
правок ядра. Новый файл-провайдер + ветка конфига + одна строка регистрации.

**З3. Обеспечить доверие к источнику личности (К4).** «Голый» заголовок
подделывается любым, кто достучался до порта. Требуется: панель доступна
только за прокси (bind на loopback) **либо** подписанные заголовки на
стороне прокси.

**З4. Provisioning учёток (К5, К6).** Автозаведение при первом входе,
привязка внешнего идентификатора (`objectGUID` / `sAMAccountName`),
`auth_provider="ad"`. Доменный администратор TDAM (`system_admin`) через AD
**не выдаётся**.

**З5. Сопоставить роли (К7).** Развилка: использовать AD-группы →
team-роли TDAM, или назначать роли внутри TDAM вручную.

**З6. Определить жизненный цикл (К8).** Что происходит с учёткой и памятью
сотрудника при блокировке/увольнении в AD.

**З7. Приёмка (К9).** На полигоне AD физически отсутствует → проверка с
ручной подстановкой заголовка. В рабочей среде — проверка с реальным AD.

**З8. Развести документацию.** Обезличенное (как работает интеграция) — в
`doc/`; специфика установки (контуры, адреса, домен) — во внутренний контур.

## 9. Связь с общей работой над инфраструктурой

Задача **выводится** из зафиксированных принципов (см. `основы-агентской-
инфраструктуры.md`):

- **единая точка администрирования** — сотрудники ведутся в AD, а не в
  параллельном реестре TDAM;
- **принцип кубика** — интеграция собирается из отдельных проверяемых
  компонентов (источник, транспорт, адаптер, доверие, роли, жизненный цикл);
- **отсутствие платных ворот на критическом пути** — AD уже в контуре;
- **источник замысла** — цель и обоснование принадлежат заказчику.
