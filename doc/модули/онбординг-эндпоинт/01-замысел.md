# 01-Замысел: онбординг-эндпоинт подключения агентов к памяти

> **Статус:** набросок для обсуждения. Решение о старте реализации — за заказчиком.
> **Автор замысла:** заказчик (dsv), 06.11.2026: «дать агенту некий эндпоинт и сказать
> "подключись к памяти"; агент что-то делает (устанавливает плагин, тянет инструкцию)
> и после этого автоматически подключается к TDAM».
> **Оформление:** агент ZCode. **Связанные документы:** `doc/стандарт-работы-с-памятью.md`
> (эталон дисциплины), `doc/правила-памяти-{zcode,dsh}.md` (адаптеры — станут
> содержимым манифестов), `doc/модули/../01-замысел.md` (этот файл — кубик 1).

---

## 1. Проблема

Подключение агента к памяти сегодня — ручная работа агента-инфраструктура:
найти мост, понять транспорт клиента, написать конфиг-блок, перенести правила,
проверить. Для каждого нового агента (цель — до 20) это повторяется. Знание о том,
*как именно* подключаться, разложено по журналу пилота и документам — агент с
чистой машины его не найдёт.

## 2. Замысел одной фразой

**Шлюз памяти становится единственным источником актуальной инструкции по
подключению.** Человек даёт агенту один URL со словами «подключись к памяти».
Агент запрашивает URL, получает манифест + исполняемую инструкцию, выполняет её
сам (правит свой конфиг, скачивает мост, проверяется) и докладывает строкой
видимости. Человек не делает ничего, кроме выдачи URL и перезапуска агента, если
тот сам не может.

## 3. Чем это НЕ является (границы замысла)

- **Не маршрутизация трафика.** Путь не выбирает протокол обработки памяти —
  REST-протокол шлюза один для всех. (См. разбор 06.11: путь `/{агент}` на
  LLM-прокси нужен потому, что LLM-протоколы разные; у памяти протокол один.)
- **Не LLM-прокси-канал.** Тема MemoryProxy (перехват LLM-трафика) не затрагивается.
- **Не автоустановка без ведома агента.** Всё делает сам агент, читая инструкцию;
  шаги, которых агент не может выполнить (свой перезапуск), — за человеком,
  и это честно помечено в манифесте.

## 4. Контракт (новое в шлюзе — два GET-маршрута)

### 4.1 Манифест подключения

```
GET /connect/{agent}/{instance}              → текстовая инструкция (markdown)
GET /connect/{agent}/{instance}?format=json  → машиночитаемый манифест
```

- `{agent}` —Known клиенты: `zcode`, `dsh` (реестр в конфиге/коде; расширяемо).
- `{instance}` — инстанс памяти (`default`); шлюз знает только свой.
- Ответ не зависит от того, кто запрашивает (нет auth на полигоне; см. §8).

**Манифест (format=json), поля:**

```jsonc
{
  "version": "2026-11-06",           // версия манифеста (дата правки)
  "agent": "dsh",
  "instance": "default",
  "gateway_url": "http://127.0.0.1:8420",
  "transport": {
    "kind": "mcp-stdio-bridge",      // единственный транспорт этапа 1
    "bridge_url": "/connect/bridge", // откуда взять мост
    "bridge_sha256": "…",            // целостность
    "client_mcp": "dsh-mcp-client | zcode-plugin | …",
    "config_block": "…"              // готовый блок под КОНКРЕТНОГО клиента
  },
  "tools": ["memory_search", "memory_capture", "memory_recall",
            "conversation_search", "memory_session_end"],
  "rules_url": "/connect/{agent}/rules",   // дисциплина (из адаптер-документа)
  "verify": { "steps": ["…"], "success": "…" },
  "manual_steps": ["перезапустить DSH"]     // что агент сделать не может
}
```

**Инструкция (markdown)** — то же самое, написанное для агента: последовательные
шаги с командами и блоками конфига, из которых агент выполняет то, что умеет.

### 4.2 Раздача моста

```
GET /connect/bridge        → tdai-mcp.mjs (тело файла)
```

Единственный источник, версия одна. Панель Memory Hub при этом остаётся
человеческим пультом (карточки прокси — отдельная тема, не эта).

## 5. Инструкции per-agent (содержимое, черновик)

### 5.1 dsh (соединяет то, что сделано 06.11 вручную)

```md
Ты — агент DSH. Подключись к командной памяти TDAM.

1. Скачай мост: curl -o C:/TDAM/tdai-mcp.mjs {gateway_url}/connect/bridge
2. В ~/.dsh/profiles/desktop/cordis.patch.yml добавь блок:
   - id: mcp-tdam
     name: "@deepseek-ai/dsh-mcp-client"
     config:
       serverName: tdam
       transport: stdio
       command: "C:/Program Files/nodejs/node.exe"
       args: ["C:/TDAM/tdai-mcp.mjs"]
3. Перезапусти DSH. (Ты не можешь перезапустить себя сам — попроси человека.)
4. После перезапуска проверь: вызови mcp__tdam__memory_search с запросом
   «тест подключения» → должна вернуться сводка памяти.
5. Перенеси правила дисциплины из {rules_url} в свой файл правил
   (раздел «Работа с памятью»).
6. Доложи человеку строкой: [память: подключено, поиск вернул N записей].
```

### 5.2 zcode

Аналогично: плагин sius-memory-tdai уже в маркете/кэше; мост — тот же файл;
конфиг — `~/.zcode/tdai-memory.json` (gatewayUrl). Шаг верификации тот же.

### 5.3 Верификация (общий хвост)

Критерий успеха один и проверяемый: **инструмент поиска памяти вызван и вернул
не пустой ответ**. Доклад — обязательная строка видимости
`[память: подключено …]`. Агент, не прошедший верификацию, докладывает об ошибке,
а не молчит.

## 6. Реализуемость (оценка по исходникам, находка → файл → что даёт)

- **Маршруты**: v2-роутер шлюза уже ветвится по `method`+пути
  (`MemoryCore/src/gateway/v2-router.ts:498` — `method === "GET" && …`);
  два новых GET — локальная правка одного файла. Трудоёмкость: малая.
- **Раздача файла**: шлюз — http-сервер на node; отдача файла без БД тривиальна.
- **Контент per-agent**: адаптер-документы уже в git
  (`doc/правила-памяти-{zcode,dsh}.md`) — манифесты собираются из них + блоков
  конфига, опробованных на пилоте 06.11.
- **Клиенты**: оба приёмника готовы и опробованы (ZCode — плагин sius-memory-tdai;
  DSH — `@deepseek-ai/dsh-mcp-client`, подтверждено README пакета в его рантайме).
- **Известный грабень**: мост при прямом запуске требует сравнения пути с
  учётом junction (фикс `isDirectInvocation` в копии 06.11) — включить в
  раздаваемый файл обязательно, иначе на машинах с junction-путями мост молчит.

## 7. Кубики (каждый проверяется отдельно, сбой различим)

| # | Кубик | Проверка отдельно |
|---|---|---|
| К1 | `GET /connect/{agent}/{instance}` (md+json) | curl → сравнить с ожидаемым текстом |
| К2 | `GET /connect/bridge` + sha256 | curl → хеш совпадает; смоук моста |
| К3 | Контент per-agent (реестр агентов, блоки конфига) | манифест dsh = блок, опробованный 06.11 |
| К4 | Верификационный шаг (текст + критерий) | прогон на DSH и ZCode |
| К5 | **Отложено**: user_key-гейт на /connect (боевой сервер) | триггер — перенос на сервер |

Сбой различим по слоям: не отдался манифест → К1; мост не запускается → К2/фикс
realpath; инструменты не появились → клиентский приёмник; поиск пуст → шлюз/память.

## 8. Безопасность

- Полигон (127.0.0.1): без auth, манифест не содержит секретов (ключ шлюза пуст).
- Боевой сервер (К5): `/connect/*` за user_key из панели (механизм User_Key есть);
  ключ входит в инструкцию, но не в сам URL маршрута. До К5 маршрут не открывать
  наружу (`host` остаётся 127.0.0.1).
- Целостность моста: sha256 в манифесте; агент может сверить.

## 9. Открытые вопросы (решает заказчик)

1. Имя пути: `/connect/…` (вариант по умолчанию) или `/onboard/…`?
2. Формат по умолчанию: markdown (агент читает текст) — согласовать, JSON по параметру.
3. Где живут тексты per-agent: в конфиге шлюза (сейчас) или в skill-хранилище
   TDAM (механизм есть, SKILL.md) — второй вариант соответствует находке 04.11
   «знания отдела как подписанные карточки, раздача через skill».
4. Версионирование моста: достаточно даты в манифесте или нужен /connect/bridge/vN?
