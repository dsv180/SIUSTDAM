# 02-Задание: перенос всей работы с памятью в MCP

> **Статус:** черновик задания на утверждение заказчика (08.11).
> Реализация не начинается до решения заказчика. Оценка трудоёмкости —
> после утверждения задания и границ (03, 04).

## Целевое состояние

Один интерфейс памяти — MCP-сервер TDAM. Все потребители (агенты, хуки,
обзорные команды пользователя) вызывают память только через него.
CLI — отладка + веб-интерфейс TDAM. Единая точка администрирования и
развития — MCP-часть; реализации не расходятся.

## Работы

### W1. Вшить MCP-сервер в шлюз (решено 08.11: вариант 2)

- **Решение заказчика:** MCP-эндпоинт становится частью самого шлюза
  (пилот-патч MemoryCore, POST /mcp на порту шлюза); отдельный
  переводчик `mcp-http.mjs` (:8900) выводится из эксплуатации после
  приёмки вшитого. Одна служба на сервере, один адрес подключения.
- Перенести логику переводчика (5 инструментов + будущие группы W2/W4)
  внутрь шлюза; конфигурация — из `~/.zcode/tdai-memory.json`
  (gatewayUrl/key не нужны — шлюз локален к себе; трио team/agent/user
  и service-id остаются параметрами вызовов).
- Патч помечается `[pilot-patch]`, переносится по регламенту ветки
  pilot-patches при каждом обновлении вендора.
- Переходный период: фасад :8900 живёт до приёмки вшитого MCP, затем
  демонтируется (ярлык автозапуска, сервис).

### W2. Инструменты подключения нового агента (группа 1)

- `connect` / `whoami` — диалог подключения по замыслу (01): агент и
  пользователь регистрируются в TDAM (команда, агент, пользователь,
  привязка актива chat_memory через v3 meta API).
- `get_rules` — выдача правил/дисциплины работы с памятью подключённому
  агенту.
- Переиспользовать наработку модуля «онбординг-эндпоинт» (К1–К3) и
  живую v3-структуру (team-2upl7r7txb).

### W3. Диалоговые инструменты (группа 2, используются хуками и агентами)

- Ревизия существующих 5: memory_search, conversation_search,
  memory_capture, memory_recall, memory_session_end.
- Состав расширений (если нужны) — собрать на этапе 03-границы.

### W4. Обзорные инструменты (группа 3, по команде пользователя)

- **Минимум = весь текущий набор обзорных функций** (решение заказчика
  08.11): поиск по памяткам L1 и диалогам L0 (уже есть как
  memory_search / conversation_search — ревизия вывода), персона (L3),
  сцены (L2 ls/read), счётчики слоёв L0–L3, последние записи.
- **Канал инструментальных ошибок** (решение заказчика 08.11: «про него
  забыли» — включить в объём): обзорные инструменты по каналу — ошибки
  за период, уроки (type=work_method), статус разбора, красные флаги
  (повтор однотипной ошибки после записанного правила). Связь с модулем
  «канал-ошибок» (папка модулей темы; план реализации из 4 итераций
  сохраняется — в MCP добавляется только обзорный слой, сам конвейер
  фиксации и доставки уроков не переизобретается).

### W5. Перевод хуков ZCode на MCP (подтверждено заказчиком 08.11)

- session-start, user-prompt, tool-hooks: вместо прямых вызовов шлюза —
  вызовы MCP-сервера (MCP-клиент внутри хука; initialize → tools/call).
- Тихая деградация сохраняется (таймаут ~8 с, недоступный MCP-сервер
  не роняет сессию).
- CLI-скрипты из хуков исключаются.
- Вшитый MCP шлюза (W1) и хуки переводятся согласованно: после приёмки
  вшитого MCP хуки переключаются на него, прямой канал закрывается.

### W6. CLI в режим отладки

- `memory.mjs` остаётся как отладочный инструмент и для обслуживания
  веб-интерфейса TDAM.
- Исключить CLI из штатных правил агентов (скилл/AGENTS/правила памяти).
- Панель Memory Hub не задевается (она ходит через свой API шлюза —
  это не CLI).

### W7. Правила агентов под MCP

- Переписать дисциплину работы с памятью (скилл komandnaya-pamyat,
  правила в AGENTS.md) на положительный контракт через MCP-инструменты.
- DSH: возврат на MCP — задание от заказчика агенту DSH (его линия;
  по запросу заказчика агент ZCode готовит текст формулировки).

### W8. Приёмка

- e2e: ZCode (инструменты + хуки через MCP), обзорные инструменты,
  подключение нового агента через `connect`.
- DSH — по приёмке его коннектора на MCP (его сторона).
- Контроль единой точки: весь трафик памяти виден на MCP-сервере;
  прямых обращений к шлюзу вне шлюза/MCP-сервера — нет (кроме панели).

## Порядок (утверждено заказчиком 08.11: логика — сначала перенос работающего, потом новое)

- **Этап 1 — перенос работающего:** W1 (вшить MCP в шлюз) + W3 (ревизия
  диалоговых инструментов) + W5 (хуки на MCP). Приёмка этапа: все
  текущие функции памяти работают через вшитый MCP; прямой канал
  закрыт. Порядок миграции живого канала — по регламенту
  («переключить скрипты канала → стоп шлюза → ...»).
- **Этап 2 — новое поверх готового интерфейса:** W2 (подключение
  агентов) + W4 (обзорные + канал ошибок) — реализовывать уже после
  того, как интерфейс стабилен.
- **Этап 3 — вывод старого из штата:** W6 (CLI в отладку) + W7 (правила
  агентов под MCP).
- **Этап 4 — итоговая приёмка:** W8.
