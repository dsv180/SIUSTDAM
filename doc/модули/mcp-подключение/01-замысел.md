# 01-Замысел: MCP-сервер подключения (вариант заказчика)

> **Статус:** замысел утверждён в расширенном виде (решение заказчика 08.11):
> **MCP — единственный штатный интерфейс работы с памятью TDAM.** CLI остаётся
> только отладочным инструментом и для веб-интерфейса TDAM; хуки (элемент
> харнесса, автоматизация без вызова модели) дергают память через MCP-сервер.
> **Предпочтение заказчика (06.11):** этот вариант — целевой; HTTP-манифест
> `/connect` (модуль «онбординг-эндпоинт») — рабочий промежуточный.
> **Автор замысла:** заказчик: «человек в диалоге даёт адрес и говорит подключись;
> агент пытается подключиться, ведёт некоторый диалог — возможно, диалог
> авторизации — и после этого получает инструкции для конкретного типа агента
> и подключается».

## Решение заказчика 08.11 (расширение замысла)

- **Одна точка администрирования**: сегодня ZCode ходит двумя каналами
  (хуки/CLI напрямую в шлюз + MCP-фасад :8900), DSH — своим прямым HTTP.
  Это несколько точек разработки и риск расхождения реализаций —
  недопустимо. Вся работа с памятью переносится в MCP.
- **Три группы MCP-инструментов**: (1) подключение нового агента — агент и
  пользователь регистрируются в памяти TDAM; (2) диалоговые — используются
  хуками и агентом в диалогах; (3) обзорные — по команде пользователя.
  Для самого MCP-сервера не важно, кто вызывает инструмент — хук, агент
  или человек: интерфейс один.
- **CLI** — отладочный инструмент и обслуживание веб-интерфейса TDAM;
  из штатных правил агентов исключается.
- **Хуки** остаются элементом харнесса (детерминированная автоматика), но
  дергают память через MCP-сервер, а не напрямую в шлюз.
- Поправка фактов: «нестабильность MCP-приёмника DSH» и «MCP не работает,
  упирается в проприетарное» — были реализационными неудачами агента ZCode
  (stdio-проводка), не свойствами платформ; CLI-канал — временное решение,
  чтобы не стоять на месте.

## Отличие от HTTP-манифеста

| | HTTP-манифест `/connect` (сделано) | MCP-сервер подключения (этот замысел) |
|---|---|---|
| Как агент получает инструкцию | сам делает curl по URL | **диалог через MCP-инструменты** |
| Авторизация | нет (К5 отложен) | **встроена в диалог** (шаг authorize) |
| Тип агента | человек назвал в URL | агент заявляет сам в диалоге (hello) |
| Раздача моста | нужен файл моста на машине агента | **stdio-мост не нужен**: шлюз говорит MCP по HTTP (streamable-http) |
| Знание об агентах | файлы-манифесты в шлюзе | состояние подключения на шлюзе |

Ключевой выигрыш: dsh-mcp-client умеет `streamable-http` из коробки; если ZCode
умеет HTTP-транспорт MCP — мост как файл исчезает из онбординга вовсе.

## Набросок контракта

Один эндпоинт шлюза: `POST /mcp` (Streamable HTTP, протокол MCP).

1. **Пока клиент не аутентифицирован** — доступен только инструмент
   `connect` (и `whoami`). Человек говорит агенту: «подключись к памяти,
   адрес http://server:8420/mcp». Агент добавляет адрес в свой MCP-конфиг,
   подключается, видит единственный доступный инструмент и вызывает его.
2. **Диалог подключения** (`connect` → возврат вопросов/промежуточных
   состояний): агент сообщает о себе (тип, версия клиента), при включённой
   авторизации — передаёт user_key (механизм User_Key панели); шлюз отвечает
   инструкциями конкретно для его типа (блоки конфига из модуля
   «онбординг-эндпоинт» переиспользуются) и выдаёт токен сессии.
3. **После успеха** — на этом же эндпоинте открываются штатные инструменты
   памяти (memory_search и т.д.); инструкции-правила агент забирает
   инструментом `get_rules`.
4. Верификация и строка видимости — как в HTTP-варианте.

## Открытые вопросы

1. HTTP-транспорт MCP у ZCode: поддерживает ли клиент `.mcp.json` тип
   `http`/`sse` (у dsh-mcp-client — подтверждено). Проверить до оценки.
2. Состояние подключения: где живёт (память шлюза / токен в клиенте) и как
   переживает рестарты.
3. Авторизация: повторно использовать механизм User_Key панели или свой токен.
4. Отношение к stdio-мосту: мост остаётся для клиентов без HTTP-MCP
   (fallback), или выводится совсем.

## Кубики (черновик)

К1 `POST /mcp` (Streamable HTTP) с одним инструментом connect; К2 диалог
подключения + авторизация; К3 раздача штатных инструментов через тот же
эндпоинт; К4 e2e на DSH и ZCode.
